# 汉化方案设计（字库 / 回写）— goal round 4

> 全部基于 **JP 原版**。

## 〇、实测空区（翻译期复核，2025）

遍历 FAT 里 1440 个**有效**条目（offset+size 落在 ROM 内的），最高占用结束于
`0x7CE6C0`，其后到 ROM 末尾是一整块连续空区：

```
0x7CE6C0 .. 0x800000   203072 字节（198.3 KB）连续空闲
（其余空档只有 8–12 字节的碎片，无实际用途）
```

**结论**：字形表 1704 × 0x80 = 218,112 字节；即使扩到 **2200 字形**（281,600 字节）
也只多出 63,488 字节，完全放得进这块 198 KB 空区。路线 B（整表搬迁扩容）
**不需要再压缩其它资源**即可完成。

## 一、硬约束（实测）

| 项 | 数值 |
|---|---|
| ROM 容量 | **8 MB，已满**（尾部 198 KB 连续空区，见上） |
| 字形表 | FAT 条目 **e850**，文件 `0x66F440`，1704 字形 × 0x80 字节 = 218,112 字节 |
| 字形格式 | 16×16，4bpp，tile 序 TL,TR,BL,BR |
| 剧本用到的字形 | **1524** 个（1704 中） |
| **可复用空槽** | **148 个**（脚本从不引用的字形槽，可安全覆盖） |
| 额外空字形槽 | 6 个（原本空白） |
| 合计可用新字位 | **约 154** |

## 二、两条扩容路线

### 路线 A：槽位复用（推荐先做，零风险）
把 148 个"脚本从不引用"的槽直接改成简体新字。
* 优点：不动表指针、不动长度、不动 FAT，改动最小
* 清单已生成：`data/free_glyph_slots.json`
* 命令：`python3 tools/font_patch.py inject <out.gba> "汉=0x026" "语=0x02E" ...`

### 路线 B：整表搬迁 + 扩容（需要更多新字时）
字形表是**资源加载**（FAT e850），代码里没有硬编码地址（已搜确认 0 处 GBA 地址字面量指向 0x66F440）。
因此可以：
1. 把字形表搬到 ROM 尾部空区 / 压缩其他资源腾出空间
2. 扩容到 N 个字形（新增字位接在末尾，索引 0x6A8 之后）
3. 更新 FAT e850 的 offset/size
* 风险：需要确认游戏**只**通过 FAT 定位字形表，且不校验 size
* 空间来源：`tools/lz77.py` 可把条目重压（实测压缩率 34–44%），
  对若干大条目重压可腾出数百 KB

## 三、字形生成（已验证）

`tools/font_patch.py` 能把系统字体渲染成**游戏原生格式**的字形：

```
16×16，0x80 字节，四个 8×8 tile 按 TL,TR,BL,BR 排列
每字节低半字节 = 左像素，高半字节 = 右像素
```

验证：渲染 `汉` 后按游戏格式解码回位图，笔画清晰正确；
注入空槽后 ROM 仅该 128 字节变化、往返一致。

## 四、容量测算（实测，关键结论）

用「日文剧本用字 + 常用简体字表」共 **1630 字** 做代理字符集测试：

```
charset size        : 1630
already in JP font  : 1355
missing (需新字形)   : 275
可复用空槽           : 148
```

**结论：只靠槽位复用不够（缺 127 个），必须走路线 B 扩表。**

→ 建议执行顺序：
1. 路线 A 先把 148 个最常用的新字塞进空槽
2. 路线 B 扩表（搬迁到 ROM 尾部空区 + 更新 FAT e850），补足剩余约 130 个
3. 若翻译能约束用字（少用生僻简体），缺口还能进一步缩小

## 五、给翻译的用字建议

为把新字形控制在 148 个以内，建议：
* 优先使用**日文字表已有的字形**（可直接用 `font_patch.py capacity` 检查）
* 避免生僻字、异体字
* 译文用词尽量贴近现有汉字的简体/日文共通形
