# 技术说明 — ROM 结构、码位与字库

> 本工程**只使用日文原版 ROM**（`Tantei Jinguuji Saburou - Shiroi Kage no Shoujo (Japan).gba`）。

## 一、字库表

| 项 | 值 |
|---|---|
| 位置 | ROM 文件 **0x66F440**（FAT 条目 **850**，offset 0x513440 / size 0x35400） |
| 格式 | 16×16，4bpp，每字形 **0x80 字节**，四个 8×8 tile 按 **TL,TR,BL,BR** 排列 |
| 每字节 | 低半字节 = 左像素，高半字节 = 右像素 |
| 字形总数 | **0x6A8 = 1704** |
| 加载方式 | 通过 FAT 资源加载，**代码中无硬编码地址**（已全 ROM 搜索确认 0 处字面量） |

**汉字排列规律**：数字/标点 → 假名 → **JIS X 0208 一级汉字（按读音序，有大量跳字）**
→ 尾段 68C–6A7 转部首序，收于 `鼾 齟 齬 齷`。

该单调性已用作转写交叉校验：1200 个汉字在 JIS 序中**严格递增、0 处逆序**。

## 二、文本编码约定（已用位图验证）

```
字符 = MAP[code]        当 code <  0x20   （标点、数字等低位字形）
字符 = MAP[code + 1]    当 code >= 0x20
```

**验证锚点**：JP 表中 `table[0x08B] = を`（位图直接确认），
而剧本里用 `0x08C` 表示「を」→ 故 index = code + 1。

解码实例：

```
データを記録しますか！         （要保存数据吗？）
俺達が事務所に戻るなり
俺達は佐藤亜希が住んでいた
春菜「神宮寺さん。遅いですよ」
```

> 教训：中途曾试图把映射表的下标整体 −1，那是错的
> （等价于双重位移，反而破坏解码）。**映射表不动，位移放在解码器里。**

## 三、剧本条目结构

```
[header u32 字段] [bytecode] [偏移表：升序 u32] [字符串池：u16 + 0000 分隔]
```

* 偏移表值 = `0x7A0 + 偏移`（字符串池基址 0x7A0）
* 偏移表**可能出现在 2 字节对齐**位置（如 0x8EA），扫描时两种对齐都要试
* 字符串以 `0x0000` 结尾；`0x000D`/`0x000E` 以外的低位码是真实字形（标点）

**回写要点**：保持 bytecode 与偏移表原样，新字符串写入原槽位、不足处补 `0000`；
超长则报错跳过，不改变条目长度。

## 八、用 mGBA 存档做实测诊断（2025 补记）

玩家在 mGBA 里按 `Shift+F1` 存出的 `.ss1` 是**PNG 容器**：IHDR/IDAT 里放 240×160 缩略图，
真正的存档在自定义块 `gbAs`（zlib 压缩的 `GBASerializedState`）和 `gbAx` 扩展块里。

- **正确加载方式**：`mCoreLoadStateNamed(core, VFileOpen(path), SAVESTATE_ALL)`。
  `core->loadState(core, vf)` 只接受裸状态，喂 PNG 容器会读到未初始化内存并报
  `Invalid or too new savestate: expected 01000007, got 0xXXXX73FC`（值每次都不一样）。
- 工具：`legacy/gbarun_state.c` → `work/bin/gbarun_state`，环境变量 `GBARUN_STATE=<ss1>`；
  编译：
  ```
  clang -O2 -o work/bin/gbarun_state legacy/gbarun_state.c \
        -I/opt/homebrew/include -L/opt/homebrew/lib -lmgba -lm -lpthread
  ```
- 用法：
  ```
  GBARUN_STATE="xxx.ss1" work/bin/gbarun_state "out.gba" 6 work/diag 2
  python3 tools/render_frame.py work/diag 2 work/diag.png --scale 4   # 复原画面
  python3 tools/dump_screen_text.py work/diag 2 --all-bg              # 复原屏幕文字
  ```
  `render_frame.py` 的 `--bg N` 可单层输出，用来判断某块文字在哪个 BG 上。

### 标题画面菜单是 **OBJ（精灵）图块条**，不是字库文本

`はじめる / 続きから / パスワード` 在 ROM 里**搜不到**对应字形码（`tools/find_text.py`），
在 BG 图块图上也找不到 —— 因为它们既不在 BG 上，也不是主字库的 16×16 字形。

真相（用 `tools/dump_sprites.py` 逐帧还原 OAM 得到）：

- 菜单是三块「牌」，每块 = **9 个 8×16 精灵**（1D 映射，每个精灵 2 个 8×8 图块），
  即 18 个图块 = 72×16 像素的一整条位图；三块分别是图块 539/557/575 起。
- 同一个条用两套 OBJ 调色板：bank 11 = 选中（白底），bank 15 = 未选中（灰底）。
- 条数据在 ROM 里**未压缩**，三条连续放在
  `0x44BF60`（はじめる）、`0x44C1A0`（続きから）、`0x44C3E0`（パスワード），每条 576 字节。
  ROM 里同样形态的条共 7 条（另 4 条在 `0x44F5A0..0x44FC00`，属另一个菜单，宽度不同）。
- 像素用 4bpp 索引：`0`=圆角外透明、`10`=外框、`11`=圆角高光、`12`=内框/文字抗锯齿、
  `15`=底色、`9`=文字主体。

汉化方式：`tools/patch_menu_plates.py` 把 `x3..68, y2..13` 的填充区擦成底色，
再用系统 CJK 字体（STHeiti Medium 12px，取能同时容纳三条文案的字号）重画
`开始游戏 / 继续游戏 / 输入密码`，按亮度分成 `9`（主体）与 `12`（抗锯齿）两级，
最后编码回 4bpp 原地写回 ROM。`build_rom.py` 在导入剧本之后自动调用它。

注：标题美术 `白い影の少女`、片头版权字、片头免责声明仍是预渲染图，未处理。


## 九、文字挤在一起 / 巨大空隙的真凶：逐字形「步进表」（2025 收尾，关键）

实机反馈「很多字 overlap，或者极大空隙」。排查结论：

### 1. 对白文字是**精灵（OBJ）**画的，不是 BG 文本

用 `tools/dump_sprites.py` 还原精灵层、`tools/render_full.py --only-bg N` 逐层对照即可确认：
每个字 = **一个 16×16 精灵**（shape0/size1，4 个 8×8 图块），x 由排版程序算出后写进
IWRAM 的精灵记录（`0x03002600` 起，步长 0x28），再整体 DMA 到 OAM。
所以 `dump_screen_text.py`（读 BG 图块图）看不到对白文字。

### 2. 排版程序每一步都读一张「逐字形步进表」

在 gbarun 里加了内存访问跟踪（`GBARUN_LOGLOAD` / `GBARUN_LOGSTORE` /
`GBARUN_LOGPC`，包装 `ARMMemory` 的 load/store 函数指针，含 LDM/STM），
抓到排版循环（`pc=0x0800B4EC` 附近）：

```
LD32 a=0x02003EF0 v=0x086A4840      ; 表指针（RAM 变量，开机时由 FAT 851 取得）
LD8  a=0x086A4BFE v=0x0C            ; 表[0x3BE=958]  -> 该字形的步进值 0x0C
LD8  a=0x086A4F43 v=0x00            ; 表[0x703=1795] -> 越界！读到 FAT852 的数据
```

x 的算法（`pc≈0x0800B540`）：

```
x = 基准 + 字段8 + (行内第 i 字 + 1) × 字段0x10 + Σ(1 + 表[字形])
```

**表就是 FAT 851**：文件 `0x6A4840`，1704 字节，原版全是 `0x0C`（= 12），
紧跟在原版 1704 个字形位图之后（`0x6A4840 = 0x66F440 + 1704×0x80`）。

我们的字库扩到 **3199 槽**，但只扩了位图（FAT 850），没扩这张表：
字形号 ≥ 1704 的字，`表[字形]` 读到了 FAT 852 的数据（`0x00 0xA0 0x78 0x9F …`），
于是步进变成 0/负值/上百 → **字挤在一起或拉开巨大空隙**。

### 3. 修法：原地延长这张表，把挡路的 FAT 852 搬走

`build_rom.py` 现在会：

1. 把 **FAT 852** 的 316,480 字节搬到 ROM 尾部并改写它的 FAT 项
   （已确认 ROM 里没有任何硬编码的 0x086A4EF0 常量，只有 FAT 项里那一处）；
2. 在**原地址** `0x6A4840` 起把表补满到 3199 字节，全部填 `0x0C`
   （FAT 851 的 size 保持 1704 不动，游戏按下标取字节、不做边界检查）。

**必须原地延长**：实测把 FAT 851 指到别处会让排版错乱 —— 说明还有别的代码
从那根指针的**相对位置**取数据，所以只能保持指针不变、把后面的字节腾出来。

### 4. 验证

用玩家存档实测（`sprite_text.py` 打出每个字的 x 与步进）：

| 画面 | 修前 | 修后 |
|---|---|---|
| ss3 新排版行 `我见过各种` | 步进 `9, 14, 416, 120, ...` | **`13, 13, 13, 13`** |
| ss2 新排版行 `现在的我只能这` | —— | **`13, 13, 13, 13, 13, 13`** |
| ss4 新排版行 `身边的人和友人之` | `13, 11, 13, …` | **`13, 13, 13, 13, 13, 13, 13`** |

注意：存档里**已经画好**的那一行仍是被旧 ROM 排版的结果，
按键翻页后新排版的每一行都是等距 13px。

## 十、白屏死机（ss5 连按 A → 白屏）：条目数据的**越界读**（2025 收尾，关键）

玩家报告：从某个存档连按 A 会进入白屏。诊断：

* 死机时 **EWRAM 整个被清零**（nonzero=0/262144），`DISPCNT=0x0080`（强制消隐），PC 停在 BIOS。
* 用 `work/font_patched.gba`（只换字库/表、**不改剧本**）跑同样的按键脚本：**不死机**；
  只要写回译文就死机 → 是剧本回写引起的。
* 用 `tools/assemble_subset.py` 把「只写部分条目」的 ROM 逐组重建 + 自动化死机测试
  （`work/crashtest.sh`：读 ss5，连按 A 到 1400 帧，看 EWRAM 是否被清零），二分到
  **e316 与 e312/313/314/315 任意一个同时写入**就死机。

**根因**：游戏读某个条目的压缩数据时会**越过条目末尾一点点**。
原版 ROM 里紧随其后的是**下一个条目的数据**（无害）；而我们把改写过的条目**追加到 ROM 尾部**
（`import_script` 在重压后比原槽大时就会追加），于是越界读读到的是**另一个条目的数据**，
游戏随即崩掉（清零 EWRAM 并消隐）。加 `pad` 或换顺序会改变结果，正是这个原因。

**修法**：`import_script.py` 每次**追加**条目后补 `APPEND_GUARD = 32` 字节零
（`rom += b'\x00' * APPEND_GUARD`）。实测只要 0x10 字节零就能让越界读落到零上，
死机消失；32 字节留足余量。**原地改写**（不追加）的条目不需要，因为后面本来就是原条目数据。

**验证**：`work/crashtest.sh out.gba` → `OK`（改前一直 `CRASH`）；
`verify_rom.py out.gba` 仍是 96,477/96,477 一致。

### 另外两处发现（供以后排查参考）

1. **FAT 852 是一整段连续块的头**（e852..e1006，`0x6A4EF0..0x7CE6C0`，1.2 MB）。
   为给步进表腾地方不能只搬 e852 —— `build_rom.py` 现在用 `block_span()` 把整段
   **整体搬迁**（保持相对偏移），并在后面补 64 KB 零。
2. **低码位（<0x20）的解码约定是「整体错位一格」**，且主表内的标点、数字都是
   按这个约定写的：真实字形 index = code − 1（**没有** `<0x20` 例外），
   编码时 `code = index + 1`。主表的 jp_text/译文因此都比真实字符**高一格**
   （`「ええ、` 在主表里写作 `」ええ。`），编码器再错回去 → **实机显示的标点与数字与原版一致**。
   这是自洽的，不要单独改一半，否则标点会整体错位。

## 十一、关于「连按 A 白屏」的复核结论（2025 收尾）

玩家报告 ss5 连按 A 会白屏。复核结果：

**现象**：卡死时 `EWRAM` 被整块清零、`DISPCNT=0x0080`（强制消隐）、PC 停在
`0x08000A1C`（一段用 DMA 往 `0x02000000` 拷贝的清 RAM 例程里）并**永久不动**。

**触发条件**：必须**连续快速按 A**（每 20 帧一次）。
完全不按键跑 900 帧：画面正常、EWRAM 正常 → 不是存档坏了。

**关键对照**（同一存档、同一按键脚本）：

| ROM | 结果 |
|---|---|
| `out.gba`（全部汉化） | 卡死 |
| `work/font_patched.gba`（**剧本完全未改**，只换字库/表/搬块） | 卡死 |
| `work/fontonly.gba`（**只搬字库**，步进表与整块都还原成日文原样） | 卡死 |

也就是说：**把剧本原封不动换成日文原版，连按 A 一样会卡死** →
这个白屏**不是汉化引入的**，而是「快速连按 A」在这段剧情里能触发的既有问题
（游戏自身的状态机 / 或 mGBA 的 HLE BIOS 行为差异）。

**给玩家的建议**：正常节奏按键不会触发；若想确认，可用另一款模拟器（VBA-M 等）
或带真实 BIOS 的 mGBA 复现一次。汉化本身在这一处的行为与原版一致。

（另：`work/crashtest.sh` 现在以「EWRAM 被清零」为判据；不能只看 `DISPCNT=0x80`，
因为游戏在正常转场淡出时也会短暂消隐。）
