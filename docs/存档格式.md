# 存档格式与「存档损坏」判定

> **游戏没有把 `.sav` 绑定到 ROM hash、译文或构建版本。** 读档先要求 EEPROM
> 读取成功，再校验存档自己的字节（魔数 + 加法校验和）。只有在模拟器确实读取了
> 同一份有效 EEPROM、没有恢复旧快照、构建保持引擎与资源结构正确的前提下，
> 改译文才不影响旧 `.sav`。不能把这条结论扩大成“任何改版或模拟器环境都不会报损坏”。
> 2026-10-15 的桌面 mGBA 对照与快照干扰实验见第八节。

本文是在日文原版 ROM 上静态逆向 + 用仓库里现有 `.sav` 实测出来的，
可用 `python3 tools/save_check.py --selftest` 复核。

---

## 一、存档设备与整体布局

存档设备是 **64 kbit EEPROM，8 KB = 1024 个 8 字节块**（`mGBA` 写出的 `.sav` 就是
这 8 KB 镜像）。EEPROM 是 MSB-first 串行传输，SDK 的读写函数会把**每个 8 字节块整体
倒序**，所以 `.sav` 里看到的是「内存镜像按块倒序」：

```
.sav 文件偏移             内存镜像（还原块倒序后）
0x0000..0x0017  块 0..2   头： [u32 校验和][u32 魔数 0x0DECADE0][w2][w3][w4][w5]
0x0018..0x001F  块 3      未用（0xFF）
0x0020..0x0ABF  块 4..343  槽 0： [u32 校验和][2716 字节负载]     （2720 字节）
0x0AC0..0x155F  块 344..683 槽 1： 同上
0x1560..0x1FFF  块 684..1023 槽 2： 同上
```

块号 ↔ 字节：`槽 i` 的起始块 = `340*i + 4`，起始字节 = `32 + 2720*i`
（游戏里的算法：`(85*i+1) << 18 >> 16`）。

### 头里的 6 个字（内存顺序）

| 偏移 | 内容 |
|---|---|
| +0x00 | u32 校验和 = `(w1+w2+w3+w4+w5) mod 2^32` |
| +0x04 | u32 魔数 `0x0DECADE0` |
| +0x08 | u8 位标志：bit0/1/2 = 槽 0/1/2 **有存档**；bit3/4/5 = 每槽一个「继续游戏」位 |
| +0x09..+0x0B | 每槽标志的其余字节 |
| +0x0C/0x0D/0x0E | 每槽摘要字段 A（来自 `0x020151A0+1`） |
| +0x0F/0x10/0x11 | 每槽摘要字段 B（来自 `0x020151A0+0x14`） |
| +0x12/0x14/0x16 | u16 每槽**游戏时间（分钟）**——实机存档界面显示成 `游戏 0时49分`，上限 0x7FFF |

> 实测：中日两个 `.sav` 的头都能对上（`0x0DECADE0` + 校验和），槽 0 有效、
> 槽 1/2 为擦除态（0xFF）。两份存档的差别只是**小时数 6 vs 2** 和几个进度字节，
> 与 ROM 版本无关。

### 槽里的 4 个字

| 偏移 | 内容 |
|---|---|
| +0x00 | u32 校验和 = 负载 2716 字节按 **679 个 u32 相加** `mod 2^32` |
| +0x04 | 2716 字节负载（游戏进度的打包快照） |

空槽（擦除态）读出来全 0xFF，校验和 0xFFFFFFFF ≠ 算出的 0xFFFFFD59，所以判为无效。

## 二、负载是什么（打包/解包）

存档前 `0x08015CA0` 把 EWRAM 里的进度变量打包进 `0x02018004`：

| 段 | 来源（EWRAM） | 长度 | 形式 |
|---|---|---|---|
| 1 | `0x0200E110` | 750 B | 每字节只存低 4 位，两个挤一发（375 B） |
| 2 | `0x0200E6EC` | 1092 B | 原样 |
| 3 | `0x0200F550` | 452 B | 原样 |
| 4 | `0x0200F714` | 8 B | 原样 |
| 5 | `0x0200F71C` | 4 B | 原样 |
| 6 | `0x0200F720` | 4 B | 原样 |
| 7 | `0x0200F724` | 1 B | 原样 |

游戏中进度变量、事件标志、道具计数都在这些区里；**没有任何字形码位文本**
（用 `work/glyph_map.ext.csv` 扫过整个负载，解不出连续可读文本），
所以改字库/译文不会污染存档内容。负载里的 2716−1936 = 780 字节是
`0x02018000` 缓冲区的其余部分，游戏也把它一起算进校验和。

## 三、「存档损坏」是怎么判出来的

| 函数 | 做什么 |
|---|---|
| `0x08015BB4` | 写头：`base[0]=0`、`base[1]=0x0DECADE0`，把 `base[1..5]` 加进 `base[0]`，再把 24 字节写成 EEPROM 块 0/1/2 |
| `0x08015C14` | 读头 → 魔数不对就重建头并把 `0x02001B9C` 置 1；魔数对就校验和 → 返回 1/0 |
| `0x08015CA0` | 打包进度变量 → `0x02018004` |
| `0x08015D88` | 算负载校验和（679 个 u32 相加）写入 `0x02018000`，再写 340 个块 |
| `0x08015DFC` | 读 340 个块，读失败最多尝试 10 次；成功后比校验和 → 返回 1（有效）/ 0（读失败或校验失败） |
| `0x08015AD0` | 读档入口：校验失败 → 状态机置 **7**；成功 → `0x08015E88` 解包 → 置 **8** |
| `0x08015E88` | 解包：负载 → EWRAM（与打包相反） |

状态 7 对应的界面文案就是 e417 第 9 条 **「このファイルは壊れています」**
（pool 偏移 `0x0C7D`）——即玩家看到的「这个文件已经损坏了」。

判定链没有 ROM 版本或译文内容校验：魔数、校验和、负载来自 EEPROM。
不过，底层读错误和负载校验错误都会进入同一个失败分支，界面文案无法区分两者。

## 四、汉化改动会不会影响存档？

| 改动 | 对存档的影响 |
|---|---|
| 改译文文字（同一个槽位内） | 无。槽位长度不变、偏移不变，存档不存文本 |
| 字库新增字形（表尾追加） | 无。旧字形码位不动（`build_rom.plan()` 用 manifest 保持槽位稳定） |
| 手工改字形 PNG | 无（存档里没有字形码位） |
| 重打包导致条目被压缩/追加到 ROM 末尾 | 存档不关心 ROM 布局；**但**条目内部偏移必须不变（见下） |
| 增删/重排主表行、改 pool 偏移 | ⚠️ 危险：引擎里有硬编码的字符串偏移与 509 条剧本分发表 |
| 给 `entry >= 1024` 的行打包 | ⚠️ 危险：`FAT[1024]` 落在 `file 0x15C000`，正是 e0 的数据区（分发表） |

要点：**FAT 只有 1024 项**（`0x15A000..0x15C000`）。`FAT[0] = (off 0, size 0xFEC)`
就是 `file 0x15C000..0x15CFEC`，引擎的剧本分发表在 `file 0x15C004`（509 条
`(keyA,keyB) → entry`，`tools/romdbg.py dispatch` 读它）。剧本入口靠它，
读档后继续演也靠它——所以这块必须和日文原版逐字节一致。

## 五、现在由谁把关

| 关卡 | 位置 | 内容 |
|---|---|---|
| 槽位预检 | `tools/check_slots.py`（`make slots`） | 译文码位数是否超过原槽位（超了会被跳过、留日文） |
| 写入范围 | `tools/verify_writes.py`（打包自检） | 改动的字节必须落在字符串槽位内：**偏移一个都不许动** |
| 引擎关键区 | `tools/verify_rom.py`（打包自检） | `file 0x15C000..0x15CFEC`（e0 数据 = 分发表）与日文原版逐字节一致 |
| entry 号上限 | `tools/import_script.py` | 出现 `entry >= 1024` 立即中止（写 FAT 会砸分发表） |
| 字形稳定 | `tools/verify_glyphs.py`（打包自检） | 字形码位 ↔ PNG ↔ manifest 一一对应，无重复、无错位 |

`make` 全绿即表示上面五条都成立。

## 六、工具：`tools/save_check.py`（模拟游戏的读档判定）

```bash
python3 tools/save_check.py --selftest          # 仓库里现有的 .sav 全查一遍
python3 tools/save_check.py my.sav              # 逐项报告 + 结论
python3 tools/save_check.py my.sav --brief      # 每个文件只打一行结论（脚本用）
python3 tools/save_check.py my.sav --resign     # 只重算校验和（不改内容）
python3 tools/save_check.py my.sav --repair     # 重算校验和 + 补魔数 + 修「有存档」标志位
```

它按游戏的两道内容判定检查文件。下表以模拟器成功读取这份文件为前提；工具不模拟
EEPROM 总线，也不检测即时存档遮蔽或模拟器实际选择了哪个文件。
`--selftest` 自动发现时排除 `work/dbg/` 和 `work/compat/` 的实验夹具；显式指定
路径仍会检查这些文件。

| 情况 | 工具怎么说 | 游戏里会怎样 | 退出码 |
|---|---|---|---|
| 头魔数 + 校验和都对，非空槽校验和也过 | `游戏能读：槽 N` | 菜单列出该槽，读档成功 | 0 |
| 头对，某个（被标志位标为有存档的）槽校验和不过 | `游戏会判损坏：槽 N` | 读该槽 → 状态 7 →「このファイルは壊れています」 | 1 |
| 头魔数不对 | `头魔数不对 → 游戏会重建头并把「有存档」标志清掉` | 菜单不再列出存档（槽数据仍在，`--repair` 可救回）⭐ | 1 |
| 头魔数对、校验和不对 | `游戏会重建头（槽数据不受影响）` | 游戏自己重签校验和，标志与槽都保留 | 按槽定 |
| 槽数据好，但「有存档」标志是 0 | `菜单不会列出来（--repair 可修）` | 菜单不列出该存档 ⭐ | 1 |
| 全 0xFF / 没数据 | `空卡 / 未初始化` | 当新卡重建头 | 1 |
| 长度不是 8192（如 512、128 KB） | `不是本作的 8 KB（64 kbit EEPROM）存档` | 需先确认模拟器导出格式；例如 gpSP libretro 预留 128 KiB，不能仅凭长度认定数据损坏 | 2 |

⭐ 这两条依据的是菜单代码路径（`0x08015C14` 清标志、`0x080159BC` 按选中槽置标志、
`0x08015580`/`0x08015B00` 按标志位分支），没有做真机截图验证；槽校验和那两条
（0/1 行）是与实际 `.sav` 数值逐字节对过的。

> `--resign` / `--repair` 是**「相信现有字节」**：按现内容重签校验和。
> 它只保证「游戏读得动」，不保证读出来的进度是对的——如果负载被改过，
> 游戏会照读那份数据。想验证「只是校验和对不上」时再用它。

## 七、复现方法（怎么自己再验一遍）

```bash
# 头：还原块倒序后，第 0 个字应当等于后 5 个字之和
python3 - <<'EOF'
import struct
d = open('侦探神宫寺三郎 - 白影的少女 (简中).sav','rb').read()
un = b''.join(d[i:i+8][::-1] for i in range(0, 24, 8))
w = struct.unpack('<6I', un)
print(hex(w[1]), hex(sum(w[1:]) & 0xFFFFFFFF), w[0] == sum(w[1:]) & 0xFFFFFFFF)
EOF

# 反汇编存档模块（需要 capstone）
python3 - <<'EOF'
import struct
from capstone import *
rom = open('Tantei Jinguuji Saburou - Shiroi Kage no Shoujo (Japan).gba','rb').read()
md = Cs(CS_ARCH_ARM, CS_MODE_THUMB)
for ins in md.disasm(rom[0x15BB4:0x15C14], 0x08015BB4):
    print(f'{ins.address:08X}: {ins.mnemonic}\t{ins.op_str}')
EOF
```

## 八、桌面 mGBA 旧档兼容性实测（2026-10-15）

反馈为普通平台 mGBA 在更新译文后的 ROM 中显示“这个文件已经损坏了”。尚未取得
反馈中实际报错的 `.sav` 和对应旧/新 ROM，因此以下是本地对照结果，不是该个案的定因。

### 有效旧档与改单句译文

使用 mGBA 0.10.5，隔离 harness，每轮新进程，从开机到标题菜单用正常按键读取槽 0，
不加载 `.ssN`，不注入剧本或修改进度。仓库已有 6 份 `.sav`，按 SHA-256 去重为 3 份：

| 原有存档 | SHA-256 前 12 位 | 新 ROM 冷启动读档 |
|---|---|---|
| 根目录中文 `.sav` | `6c50c48f8aa5` | 正常，e1 葬礼调查 |
| `work/campus-save/office-saved.sav` | `976714e92ec0` | 正常，e57 事务所 |
| `work/campus-save/probe-saved.sav` | `1a53da89bd10` | 正常，e100 校园 |

三份文件的头与槽 0 校验均有效，读档后的剧本结构均完整匹配。使用的发布 ROM
SHA-256 为 `be05afcab46d58b51642474c98ac3d933d03a3243db9829865bf7cdf1efca79d`。
此前事务所存档的验证记录还指向补齐前 ROM `bc1d2166…`，因此确实包含跨构建读取。

另从旧汉化 ROM 复制一份，只把 e57:5 的“我听见一阵**细微**的响动。”改为
“我听见一阵**轻微**的响动。”，经真实 `import_script.py` 重压缩并补齐 16 MiB。
旧事务所 `.sav` 仍成功读取，画面显示新译文“轻微”。实验 ROM 的 SHA-256 为
`cef252a1562179f4a20a93fb946ad2481f48fe7cf76d3762e176e5cbcd8ce40a`。
该译文只写到实验副本，未改主翻译表或根目录 ROM。

负面对照在事务所存档的**副本**文件偏移 `0x100` 翻转 1 bit，未重算校验和。
`save_check.py` 报槽 0 校验错误；同一 mGBA 冷启动流程确实显示
“这个文件已经损坏了”。这证明工具判定与实际错误界面对应，并非把未进入游戏
误认为读档成功。原有 6 份存档在测试前后 SHA-256 全部不变。

静态核对还确认：发布 ROM 与日文原版的 `[0, 0x15A000)` 代码区逐字节相同，
包含 `0x08015DFC` 读档校验。没有找到“译文改变后必须重新签名旧档”的机制。

### 即时存档可以遮蔽有效 `.sav`

本机 mGBA 配置当时为 `autoload=1`、`autosave=0`、`saveStateExtdata=31`、
`loadStateExtdata=9`。检查官方 0.10.5 源码可见：

- [`CoreController`](https://github.com/mgba-emu/mgba/blob/0.10.5/src/platform/qt/CoreController.cpp#L52)
  在启用 autoload 时尝试恢复 slot 0 自动快照。
- [`mCoreLoadStateNamed`](https://github.com/mgba-emu/mgba/blob/0.10.5/src/core/serialize.c#L530)
  只要快照含 savedata 就调用恢复函数；`SAVESTATE_SAVEDATA` 标志控制写回方式，
  不是完全忽略附带 EEPROM。
- [`_GBACoreSavedataRestore`](https://github.com/mgba-emu/mgba/blob/0.10.5/src/gba/core.c#L1222)
  在未设置该标志时调用 `GBASavedataMask`，让游戏暂时读取快照内的数据。
- [ROM CRC 不一致](https://github.com/mgba-emu/mgba/blob/0.10.5/src/gba/serialize.c#L116)
  本身仅产生警告，不能指望模拟器必然拒绝跨译文版本的快照。

额外对照：用含上述坏档的旧 ROM 在开机第 1 帧生成测试快照；新 ROM 先加载
**有效事务所 `.sav`**，再按本机 `loadStateExtdata=9` 恢复该快照，随后正常按键读档。
结果仍显示“这个文件已经损坏了”，磁盘上的原 `.sav` 完好。使用的是实验 harness
副本，只调整存档/快照载入顺序与 flags 来复现 GUI 语义，没有修改游戏代码或 RAM。

此实验只证明“有效磁盘存档被快照中的坏内容遮蔽”可以产生相同症状。
本次未找到根目录对应的 `.ss0`，也没取得用户出错时的快照；不能断言反馈就是此原因。
不要把 `loadStateExtdata` 未选 savedata 当作彻底禁用快照干扰的保证。

### 排查实际报错文件

1. 保留报错 `.sav` 原件，先运行 `python3 tools/save_check.py '实际文件.sav'`，
   不先执行 `--repair` 或 `--resign`，以免掩盖损坏位置。
2. 在独立目录放入新 ROM 和同名 `.sav` 的副本，关闭自动载入即时存档，完全重新
   开机并从标题菜单选择“读取”。不要恢复旧 `.ss0` / `.ssN`。
3. 同一份 `.sav` 副本分别在旧、新 ROM 冷启动验证。如果仅新版失败，需保存这对
   ROM 的哈希、模拟器版本与报错槽位，继续定位引擎或 EEPROM 读取差异。

本次证据位于 `work/compat/old-save/`：`inputs.json`、`summary.json` 保存哈希与结构
结果；`mgba-old-save-load.png`、`translation-vs-damage.png`、`state-shadow.png` 为
实际游戏截图；各组同时保留原始 PPM、RAM 与运行日志。测试快照、坏档副本、实验
ROM 均留在该目录，不作为玩家存档或发布产物。

三份旧档和改单句实验的共用读档输入为 8,500 帧：

```text
START@5000:4 DOWN@5300:4 A@5500:4 A@6000:4 A@6300:4 LEFT@6600:4 A@6800:4
```

可通过 `tools.harness_utils.run_harness` 的 `sav=` 参数提供存档，`state=None`
保证本轮不恢复快照；目标场景应由截图及 `entry_id.resolve_from_ram` 一起核对。
