# 动态测试：可复现的无头回归

> 2026-10 立。补的是**动态侧**：静态侧（`make verify`、槽位预检、存档校验）一直很严，
> 但实机跑出来的东西一个都没留下——`work/` 全被 gitignore，即时存档和截图跑完就丢，
> 历史验证都是「人工敲一遍 harness + 人看结论」。于是 `docs/存档卡死分析.md` 那类
> **只有走到某个分支才会暴露**的问题，只能靠人撞见。

## 零、地基：模拟器是确定性的

整套东西成立的前提，2026-10 实测确认：

```bash
# 同一份即时存档 + 同一串按键，跑两次，比 RAM 与帧缓冲
GBARUN_STATE=work/dbg/base.ss1 GBARUN_RAMSNAP=400:/tmp/k1 \
    work/bin/gbarun_dbg "<cn>.gba" 401 /tmp/k1 A@120:4 A@240:4 A@300:4
GBARUN_STATE=work/dbg/base.ss1 GBARUN_RAMSNAP=400:/tmp/k2 \
    work/bin/gbarun_dbg "<cn>.gba" 401 /tmp/k2 A@120:4 A@240:4 A@300:4
md5 /tmp/k1.ewram /tmp/k2.ewram     # 相同
md5 /tmp/k1.iwram /tmp/k2.iwram     # 相同
```

冷启动 600 帧两次的 `.ppm` 也逐字节相同（`a689563987a5a9a511a10123071b917b`）。

**结论**：`EWRAM / IWRAM / VRAM / 帧缓冲` 都可以当精确证据做哈希比对，比"看图"硬得多。
同样地，预测/观测的**位级**比对在这里是可行的（这也是为什么「按键脚本 + 帧号」能替代
提交即时存档）。

⚠️ 两个绑定关系别忘：

* 即时存档与 ROM 构建版本绑定（`docs/调试器.md` 第五节），换构建就得重做；
* 因而**存档不入库**，入库的是「冷启动 + 按键脚本」和跑出来的**哈希**。

## 一、`make check-dyn` —— 动态回归主体

```bash
make check-dyn                 # = check_append_guard + dyn_check run
make test-unit                 # 工具自身的回归，不需要 ROM / 模拟器
make test                      # 工具单测 + 静态校验 + 索引 + 存档 + 动态路线
make autoplay                  # 完整通关路线，正常按键输入，无需 AI
make dyn-list                  # 列出规格里的检查
make dyn-update                # 用当前结果刷新基线
python3 tools/dyn_check.py run --only cn-boot --strict --json
```

* **规格**：`tests/dyn/checks.json`（入库）
* **基线**：`tests/dyn/baseline.json`（入库，几 KB）
* **证据**：`work/dyn/<检查名>.<rom>.{ewram,iwram,vram,ppm,log}`（不入库，可随时删）

完整游玩与短回归分开运行：`make autoplay` 使用
[`tests/autoplay/route.json`](../tests/autoplay/route.json) 从冷启动走到结局密码画面，
严格核对全部分段的 RAM 和画面哈希。运行依赖、断点续跑和退出码见
[`tests/autoplay/README.md`](../tests/autoplay/README.md)。

运行前验证规格、按键和帧数。未知不变量、重复名称、没有匹配用例均报错；
帧号从 0 开始，按键必须落在运行范围内。每次模拟器默认限时 60 秒，可在检查中用
`timeout` 指定。全部继承的 `GBARUN_*` 调试变量都会被清除，并禁止自动读卡带存档。
每次使用独立临时目录收集证据，检查退出码、RAM/截图长度及采样完整性；运行失败不会复用旧快照。

一条检查 = **从冷启动开始的固定按键路线 + 一组不变量**。

```json
{
 "name": "cn-boot-funeral",
 "rom": "cn",
 "frames": 5500,
 "keys": ["START@5000:4", "A@5300:4"],
 "sample_every": 500,
 "invariants": {
  "live": true, "entry_is": 438, "rows_is": 30, "row_is": "438:0",
  "line_contains": "哲司", "ewram_nonzero_min": 4096
 }
}
```

按键写法：`A@120:4`（第 120 帧按 4 帧）；`A@5000-5600:4:40`（区间内每 40 帧按一次）。

### 不变量一览

| 键 | 含义 |
|---|---|
| `live` | 末帧引擎在演剧本（池基址/当前行都是有效值） |
| `entry_is` | 反查出的条目号（见第三节） |
| `rows_is` | 描述符里的 keyCount |
| `row_is` | `entry:idx` 形式的译文表行号；按实际文本偏移匹配，不能直接用引擎行表下标 |
| `line_contains` | 当前屏上的文本包含某串（**只对 cn 判定**，JP 字库映射不同） |
| `ewram_nonzero_min` | EWRAM 非零字节数下限；**0 = 白屏/被清零**，这是最便宜的崩溃探针 |
| `no_stall` | 相邻有效采样之间位置变化次数下限；`true` 等于至少 2 次，需设置 `sample_every` |
| `same_*` | 差分不变量：`same_entry` / `same_rows` / `same_rid`，只在 `rom: "both"` 时有效 |

### 差分模式（`"rom": "both"`）

同一条按键路线在**日文原版**和**简中补丁**上各跑一遍，要求两边落到同一个条目、
同样的 keyCount、同一行。这是「静默分支损坏」的最小探测器——不需要事先知道正确剧情，
只要两份 ROM 行为一致。分发表（`file 0x15C000..0x15CFEC`）本来就由 `verify_rom.py`
保证与 JP 逐字节一致，所以 entry 号在两份 ROM 之间可以直接比。

### 哈希漂移不是失败

改一句译文就会让 EWRAM/VRAM 哈希变（文本就在里面）。所以：

* **不变量**不成立 → `FAIL`，退出码 1；
* 哈希与基线不同 → `PASS*` + `证据漂移`，退出码仍是 0（加 `--strict` 才算失败）。
* 缺少基线、缺少证据哈希或路线规格变化同样算漂移；`--strict --json` 的 `pass` 与退出码一致。

`--update` 只有在所有选中用例的不变量与执行检查全部通过后才原子写入基线。
`--only ... --update` 保留未选中的检查；每条基线各自记录 ROM 哈希与规格指纹。
更新失败时原文件不变。`--update --json` 只输出一个 JSON 对象；`--strict` 与 `--update` 互斥。
基线需在核对落点与证据后刷新，不能拿它掩盖行为失败。

这样 `make check-dyn` 可以天天跑而不吵人，而真正"行为变了"才红。

## 二、`check_append_guard.py` —— 把当年的 crashtest 变成静态检查

已并入 `make verify`。检查的是「追加条目」的两条硬约束（`docs/技术说明.md` 第十节）：

| 约束 | 违反后的症状 |
|---|---|
| 追加偏移必须 4 字节对齐（BIOS LZ77 SWI 的要求） | 解压失败 → 笔记本/存档界面「花形乱码字」 |
| 追加数据后必须补 32 字节零（`APPEND_GUARD`） | 越界读读到别的条目数据 → 白屏、EWRAM 被清零 |

```bash
python3 tools/check_append_guard.py                       # 参照 work/font_patched.gba
python3 tools/check_append_guard.py --rom /tmp/bad.gba     # 验任意产物
```

参照 ROM = **同一次构建、但没写过剧本**的那份（`build_rom.py` 会存成
`work/font_patched.gba`）。FAT 与参照不同、且偏移也变了的条目就是「追加」。

这两条本来就是构建产物的静态性质，当年用 `work/crashtest.sh` 二分是因为还没定位到根因；
现在不需要模拟器、也不需要即时存档就能验。`tools/assemble_subset.py` 也已同步补上
对齐 + guard，否则它拼出来的子 ROM 会**假崩**。

## 三、`crash_bisect.py` —— 真出崩溃时的二分

留给「静态检查全绿、实机仍然炸」的情况。

```bash
python3 tools/crash_bisect.py --self-test              # 只验证二分逻辑（不跑模拟器）
python3 tools/crash_bisect.py --state tests/dyn/ss/repro.ss1 \
        --keys "A@60-1399:4:20" --frames 1400
```

* `--base work/font_patched.gba`、`--full <简中 ROM>`、`--state <起点 .ss1>` 必须**同一次构建**；
* 判据：跑完后 EWRAM 非零字节数 < `--min-nonzero`（默认 16）即为白屏/清零，
  可加 `--use-dispcnt` 额外要求 DISPCNT 处于强制消隐；
* 算法：ddmin（分块与补集缩减，再逐个剔除），结果缓存，`--max-runs` 默认 120；
* 空集参照也崩时拒绝归因；候选同时比较 FAT 与资源内容，包含长度不变的原地改写；
* 子 ROM 保留原地资源地址，只对搬迁条目追加并补齐对齐/零 guard；FAT 仅允许 0..1023；
* 每次运行验证即时存档实际加载成功、退出码与证据完整性，支持 `--timeout`；
* 起点存档放 `tests/dyn/ss/`（见下），它**不会被 `make clean` 删掉**。

## 四、entry 号反查：覆盖率目标的坐标系

`where` 以前只能报「池基址 / 行数 / 游标」，报不出条目号，于是观测是一串无意义的地址。
现在由 `tools/entry_id.py` 反查（只用 ROM + RAM，不依赖任何 `work/` 产物）：

1. 描述符 `0x02003F24` 里已经有钥匙：`+0x10` = keyB、`+0x14` = keyCount；
2. ROM 分发表（`file 0x15C004`，509 条）按 `(keyCount, keyB)` 筛候选（实测每组 ≤7 个）；
3. 把 RAM 缓冲与候选条目的解压数据逐字节比：先比**结构区** `[0x000, 0x7A0)`
   （头部 + 流程/标志区，与译文无关），再比文本区比例兜底。

实测 `work/dbg/base.ss1`：候选 `[438, 469]`，e438 结构区 **1952/1952 全中**、
竞争者 1944/1952 → 判定 **e438**，场景 **438.0**，行 **438:0**，`jp/cn = 哲司“““`。
与 `data/scene_lines.tsv` 完全对上。（这份存档来自旧构建，文本区有 137 字节差异，
所以第 3 步的「结构区优先」是必须的。）

```bash
$ python3 tools/state_inspect.py where work/dbg/base.ss1
   池基址 0x02030AA0  缓冲 0x02030300  keyCount 30  rom 0x08651BF0
   游标 0x014C → 第 0 项   当前行 off 0x01C2
   文本 哲司“““
   条目 e438  场景 438.0  [结构区全中，窗口 3251/3388，候选 2 个]
   行 438:0  jp=哲司“““
              cn=哲司“““

$ python3 tools/state_inspect.py entry work/dbg/base.ss1
work/dbg/base.ss1	e438	438.0	438:0
```

`tools/romdbg.py where` 同样会多打这几行。多个存档一起看就用 `state_inspect.py entry`。

## 五、目录与 gitignore 约定

| 路径 | 入库 | 说明 |
|---|---|---|
| `tests/dyn/checks.json` | ✅ | 检查规格 |
| `tests/dyn/baseline.json` | ✅ | 证据哈希基线（几 KB） |
| `tests/dyn/ss/.gitkeep` | ✅ | 占位，保证目录在 |
| `tests/dyn/ss/*.ssN` | ❌ | 复现用起点存档：与构建绑定，但**不能**被 `make clean` 删 |
| `work/dyn/`、`work/crashbisect/` | ❌ | 每次跑出来的证据与子 ROM，可随时删 |

为什么不把 `.ssN` 入库：它和 ROM 构建版本绑定（改字库/搬块后一律作废），
入库只会留下一堆用不了的死文件。**入库的是「怎么跑」和「应该得到什么哈希」。**

## 六、怎么加一条检查

1. 先手动把路线走通：

   ```bash
   python3 tools/romdbg.py play --state work/dbg/base.ss1 --frames 3000 \
           --keys "A@600:4 A@1200:4" --shot-every 200
   python3 tools/state_inspect.py where work/dbg/play/some.ss1   # 或看末帧截图
   ```

   ⚠️ 一句话至少给两次 A（第一下补完打字机，第二下才翻页）；
   剧情中的弹出选项会把游标钉住，必须按 A 选掉。

2. 把「启动方式 + 帧数 + 按键」抄进 `tests/dyn/checks.json`，先只写 `{"live": true}`。

3. `python3 tools/dyn_check.py run --only <名字>`，看报告里的 `e…/场景/行`，
   确认落点**符合预期**（回去对 `data/scene_lines.tsv`），再把它固化成
   `entry_is` / `row_is` / `line_contains`。不要直接把跑出来的值抄成期望值——
   那样只能测出"没变"，测不出"本来就错"。

4. `python3 tools/dyn_check.py run --update` 记下证据哈希。

## 七、已知边界

* **只能从冷启动起步**：因为存档不入库。想验收「某一幕的第 200 行」只能靠正常走到，
  或者用本地手工存档跑 `romdbg.py play`（一次性验证，不进回归）。
* **没有「跳到任意一行」**：文本级注入是禁区（`AGENT.md`、`docs/调试器.md` 第四节）。
* **差分只比结构，不比像素**：标题/职员表是预渲染图，简中改过图，逐像素比没有意义；
  要比也是各自和自己过去的哈希比。
* **哈希会随译文漂移**：这是预期行为，不是 bug。
* **`no_stall` 是启发式**：靠「按键后游标变了几次」判「按键没推进」，
  所以只对明确会推进的路线开（比如连按 A），别给会停住等输入的场面开。
* **二分不等于证明根因**：即时存档已包含载入的剧本与指针；修改当前已载入条目
  可能要到下一次正常载入才生效。参照与全集必须可复现地表现不同，结果仍需正常路线复验。
* **模拟器速度**：一条 5500 帧的冷启动路线约 2 秒；当前 5 条检查包括最长 77253 帧的书斋完整调查路线，
  可以进日常流程。要做全场景覆盖得按「条目/场景」分片，别指望一次跑完整个游戏。
