# 打包流程（译文 → 可玩 ROM）

> 输入：`data/translation.tsv`（45484 行已译）+ 日文原版 ROM
> 输出：`out.gba`（中文 ROM）

## 一、一条命令

```bash
python3 tools/build_rom.py --out out.gba
```

它做两件事：

1. **重排字库表** —— 译文用到 **2102** 个不同汉字，日文字库只有 1704 槽，
   其中 931 个可直接复用，**1171 个要新做**。
   新字**全部追加在表尾**（0x6A8 之后），**不覆盖任何原有槽位**——
   因为标题画面、菜单、图形界面的字形也在这张表里，覆盖会破坏它们。
2. **回写剧本** —— 调 `import_script.py --map work/glyph_map.ext.csv`，
   按扩展映射把译文写回每个字符串槽位（就地改写 + LZ77 重压，放不下就追加并改 FAT）。

## 二、字库表放哪：ROM 扩容

| 项 | 值 |
|---|---|
| 新表大小 | 3003 字形 × 0x80 = **384,384 字节**（1704 原字 + 1171 新字 + 128 备用槽） |
| ROM 尾部空区 | `0x7CE6C0..0x800000`，**203,072 字节**（装不下 384 KB） |
| 因此 | 表放到 **文件 0x800000**，ROM 由 8 MB 扩到 **8.37 MB**，FAT e850 指向它 |
| ROM 头部 | GBA 头部**没有** ROM 尺寸字段（0x80 属于 logo），扩文件不需要改头部 |

这条路与参考中文版一致（`tools/build_jp_map.py` 记录过「CN 表在 file 0x800000」），
且**不需要改任何代码**：字形表是通过 FAT 资源定位的，字形直接从 ROM 读。

## 三、编码约定（本次实测校正，很关键）

```
下标 < 0x20 :  码位 = 下标
下标 ≥ 0x20 :  码位 = 下标 + 1        ← 注意是 +1
```

位图实证：

* 表下标 `0x08B` 的位图是 `を`，而剧本用码位 `0x08C` 表示 `を` → `下标 = 码位 − 1`
* 表下标 `0x020` 的位图是 `×`，而剧本用码位 `0x021` 表示 `×` → 同上

> ⚠️ 曾经的坑：`import_script.reverse_map()` 写的是 `码位 = 下标 − 1`（差 2），
> 生成的 ROM 会让游戏显示**低两个下标**的字（写「要」显示「用」）。
> 已修正为 `下标 + 1`；`tools/verify_rom.py` 用同一约定解码，可当场发现这类错误。

| 真机画面 | `work/bin/gbarun`（libmgba 无头）+ `tools/render_frame.py` | 标题画面与日文原版**逐像素一致** |

## 八、字形风格必须与母语字库一致（重要）

实测日文原版 ROM：**1703 个非空字形全部只用两个像素值**。

| 项 | 规格 |
|---|---|
| 用色 | 只有 `1`（字身）与 `2`（投影）；**没有**其它灰阶 |
| 字身 | **11×11 设计框**，位于单元格 `(0,1)`（中位 11×11，最大 12×12） |
| 投影 | 字身**右侧 1px**（29576 个右邻 + 12647 个拐角；仅 3 个下方），自动生成 |
| 墨量 | 字身平均 **50.5 像素/字**；字身:投影 ≈ **65:35** |

**教训**：最初用系统字体直接渲染成 1–15 全灰阶、填满 16×16，
而游戏文字调色板是灰阶表（索引 1=(80,80,80)、2=(104,96,88)、**15≈(232,208,184) 接近白色**），
于是实心笔画落在浅色上 → 又细又淡、比原字大一圈。

现在 `font_patch.render_glyph()` 按上表量化：
字体 18px → 缩放进 11×11 设计框 → 阈值 90 取字身 → 右侧自动补投影。
与 150 个原版字形对比：字身 51.1 px/字（原 50.5）、投影比 68.6:31.4（原 65.3:34.7）。

### 8.1 换成像素字库 zpix（推荐，已默认）

把 18px 轮廓字体缩到 11×11 再二值化，笔画经常断、粗细不匀（实机上就是“糊”）。
现在改用**点阵像素字体**：`tools/fonts/zpix/zpix.bdf`（Zpix 最像素，12px，
CJK 字形正好 **11×11**，与本作设计框完全一致，覆盖我们新增的全部 1369 个字）。

* `tools/pixelfont.py` 直接解析 BDF，取原始位图，不缩放、不抗锯齿；
* 摆放按字体自身基线：CJK 落在设计框 `(0,1)`；标点/数字/拉丁按自己的
  `BBX` 偏移摆放（如 `、` 落在 `(2,9)`、`。` 落在 `(1,8)`、`…` 落在 `(0,8)`，
  与原版字体同类标点的位置一致）；
* 投影仍是「字身右侧 1px」，与原版一致。

对比工具：`python3 tools/font_compare.py --out cmp.png --text "一行中文"`，
会按**游戏实际显示方式**渲染两遍（上=轮廓缩字，下=zpix），JP 字库已有的字两次
完全相同（那些槽是复用原版的），只有新增字不同；样例见 `docs/字形对比.png`。
`--rom out.gba` 则直接按打包结果里的字库渲染（即实机画出来的位图）。

回退：`python3 tools/build_rom.py --outline-font`（或删掉 `tools/fonts/zpix/`）。

> **授权提醒**：Zpix 对**个人 / 教育用途免费**，商业产品需向作者付费（README 标价
> USD 1000）。本项目是免费同人汉化，属个人用途；若将来要商用，请换 OFL 授权的
> 点阵字库（如 Ark Pixel 方舟像素），`tools/pixelfont.py` 按 BDF 读取，换文件即可。

## 九、字形 PNG 底稿与手工改字

```bash
python3 tools/export_glyphs.py                                              # 整表导出到 data/glyph_png
# ... 在 data/glyph_png 里手工改字 ...
python3 tools/build_rom.py --out out.gba                                    # 重新打包（自动套用改字 + 自检）
```

**每个字只有一张图**（`data/glyph_png/README.md` 有完整说明）：

| 文件名 | 含义 |
|---|---|
| `{字}.png` | 该字正式字形槽（编码器实际写入的最低下标槽） |
| `{字}（新）.png` | 中文版**新追加**的字形（下标 ≥ 0x6A8），便于优先手工调整 |
| `重复_{下标}.png` | 同字的其它槽位；正式文件上的改动会**同步写进这些槽** |
| `未使用_{下标}.png` | 未分配文字的槽位 |

* 导出图用**游戏原生文字调色板**渲染，所见即所得；`manifest.tsv` 记录
  `file / index / code / char / is_new / role / ink`。
* 目录里过期的 PNG 由导出脚本自动删除，目录内容始终与 ROM 一致。
* 导出脚本**拒绝覆盖「改过但还没导入 ROM」的 PNG**（退出码 2，需 `--force`），
  防止手工改字被静默冲掉。
* `import_glyphs.py` 按**字**为单位写入：改一张图 → 该字占用的所有槽位一起更新
  （日志里的 `duplicate slots re-synced` 就是这个数量）。
* `build_rom.py` 在打完字库后**自动套用 `data/glyph_png` 的手工改字**
  （`[phase] applying hand-edited glyphs`），所以重新打包不会把手改的字形冲掉；
  若目录与本次渲染差异超过 200 个字形（说明目录来自别的 ROM），打包会中止并提示
  `--force-glyph-edits`。
* 自检 `tools/verify_glyphs.py` 检查四件事：译文用到的字都有非空字形、
  每个字只有一张正式图、PNG 与 ROM 同步、manifest 与字库槽位一一对应；
  不通过则整次打包判定失败。

## 十、串池条目导致的大漏译（已修复）

整批被跳过。修复：

* `import_script.py` 支持串池行按**绝对偏移原位改写**
* 主表 45,488 → **59,877 行**（新增 14,396 行池行）

**另修的坑**：e21/e311/e314/e428 同时存在「偏移表行」与「串池行」，两类 `idx` 撞车，

## 十一、标题画面菜单是 OBJ 图块条（已汉化）

`はじめる / 続きから / パスワード` 既不是字库文本、也不在 BG 上，而是**精灵（OBJ）拼的牌子**：
每条 = 9 个 8×16 精灵 = 18 个图块 = 72×16 像素的整块位图，数据**未压缩**放在
`0x44BF60 / 0x44C1A0 / 0x44C3E0`。`tools/patch_menu_plates.py` 擦掉日文笔迹后
用 CJK 字体重画 `开始游戏 / 继续游戏 / 输入密码`，按亮度分 `9`（字身）/`12`（抗锯齿）两级写回。

`build_rom.py` 在导入剧本后会自动调用它，无需手工执行。标题另一块牌子
`PRESS START BUTTON`（`0x44BC00`，13 个精灵）本身就是英文，未改。

## 十二、模拟器即时存档（.ssN）是**按 ROM 版本**的，不能跨版本用来验收

实测结论（2026-09）：

* 即时存档里存的是**当时的 VRAM/RAM 快照**，不是「指向 ROM 的引用」。
  用新 ROM 载入旧存档时，对话框里显示的还是**旧版本当时的字形与文本**，
  看起来像「漏译」，其实 ROM 里已经是中文了。
* 旧存档里的**剧本指针**指向旧版本追加数据的位置。新版重新打包后这些位置变了，
  继续按 A 推进就会跑到别的数据上——表现为白屏 / 游戏自己复位
  （EWRAM 被清 0、`DISPCNT=0x0080`、PC 落在启动代码 `0x08000A1C`）。
* 对照实验：同一个旧存档 + 「只换字库、剧本完全没动」的 `work/font_patched.gba`
  也一样崩；而**从冷启动**用同样的「每 40 帧按一次 A」连打 6000 帧，
  日文原版与中文版行为一致（EWRAM 非零字节数 28778/28840 对 28777/28839）。
  所以这不是翻译造成的。

**验收规则**：换 ROM 后**不要**读旧的即时存档。要么从标题重新开始，
要么用游戏内的存档（SRAM，只存进度不存 RAM 布局），要么用新 ROM 重新存一份 `.ssN`。

## 十三、存档 / 读取界面同样是预渲染图块（尚未汉化）

用 `ss1` 即时存档（存档界面）核对后确认，界面上这些字**都不是字库文本**，
`find_text.py` 在 ROM 里也搜不到 `セーブ` / `ロード`（说明不是被压缩藏起来的文本）：

| 位置 | 内容 | ROM 里的图块块 |
|---|---|---|
| 左上 | `SELECT`（英文，原本就是英文） | `0x44E1C0 / 0x44E240 / 0x44E2C0` |
| 三个 FILE 条 | `□ / プレイ 時間 分`、竖排 `FILE` | `0x44E8E0 / 0x44ECE0 / 0x44F0E0`（各 32 图块 = 64×32） |
| 左侧菜单 | `セーブ` / `ロード` / `消去` | `0x44F5A0` 起（每项 2×16 图块 = 64×32） |
| 小图块 | `□`、`/` | `0x450120 / 0x450140 / 0x450160` |
| 8×8 字块 | `プレイ`、`時間`、`分` 的笔画块 | `0x461AB0` ~ `0x461CF0` |

判定方法：从即时存档的 dump 里读 OAM，把精灵用的图块号换算到 VRAM 的 OBJ 区
（`vram+0x10000+tile*32`），再回 ROM 里搜同样的字节 —— 这些图块在 ROM 里是
**未压缩**存放的，和标题菜单的三块牌子（`0x44BF60` 等）一样，所以汉化方式也一样：
擦掉日文笔迹、用 CJK 字体重画。目前 `patch_menu_plates.py` **只改了标题菜单那三块**，
存档界面的这些块还没动。

> 顺带确认：存档界面下方那几行 `3月11日` 是**字库文本**（精灵逐字绘制，前面 5 格是
> 空格填充），日文原版 ROM 加载同一个即时存档时会在同一位置画同样的东西，
> 所以位置是游戏本来的排版，不是我们改坏的。

## 十四、存档 / 读取界面的汉化（预渲染图块，已处理）

第十三节记录了位置，实际改写工具是 `tools/patch_save_plates.py`（`build_rom.py` 在标题
牌子之后自动调用）。注意这些图块**不是一个整块**，而是按精灵切分的（1D 映射下，
32 像素宽的精灵每行 4 个图块，64 像素宽的每行 8 个）：

| 目标 | ROM 位置 | 原图 | 现译 |
|---|---|---|---|
| 存档条目第 2 段 | `0x44ECE0`（64×32） | `プレイ`（x 17..38）+ `時`（x 55..63） | `游戏` |
| 存档条目第 3 段 | `0x44F0E0`（64×32） | `間`（x 64..73）+ `分`（x 89） | `时`（`分` 未动） |
| 菜单项 1 | `0x44F5A0` + `0x44F6A0`（各 32×16） | `セーブ` | `保存` |
| 菜单项 2 | `0x44F7C0` + `0x44F8C0` | `ロード` | `读取` |
| 菜单项 3 | `0x44F9E0` + `0x44FAE0` | `消去` | `删除` |

**坑一**：`プレイ時間` 四个字是**跨精灵**的 —— 第 2 段存的是 `プレイ時`，第 3 段存的是
`間` 和 `分`。所以工具把这两段拼成一个 128×32 的画布，`分`（画布 `x=89..97`）保持原样。
（第一版没注意，把 `分` 一起擦掉了，实机截图才发现。）

**坑二（后修的）**：这一行**不是**一个连续标签 —— 游戏会把游戏时间**画进这行里**，
日文界面实际是

```
プレイ [时数] 時間 [分数] 分
```

即 `プレイ` 是标签、`時間` 是**时数的单位**（分的单位是后面的 `分`）。所以第一版把
`游戏时间` 当一整条画出来，`时间` 正好画在时数数字的位置上，实机里那个 `0` 就压在
`时间` 上（玩家看到的「游戏时间 和一个 0 重叠」）。

数字槽位（实测 OAM）：时数在画布 `x 47..54`（屏幕 `x=175`），分钟右对齐到画布
`x 74..88`（屏幕 `x=216`）。所以现在的画法是**两个独立标签**：

* `游戏` 画在 `プレイ` 的槽位（画布 `x 16..45`），右端 170 < 175，不碰数字；
* `时` 画在 `時間` 的槽位（画布 `x 55..73`）—— 这里只有 19px 宽，而分钟数字从
  `x 74` 起，所以单位只能用**单字**：`小时` 要 23px，要么被压缩要么压到分钟数字上。

实机显示：`游戏 0时 40分`（空档位是 `游戏 时 分`）。

字号/配色按原图实测：存档条目的字用调色板索引 `1`（原图无抗锯齿），
菜单项用 `9`（字身）+ `12`（抗锯齿），底色分别是 `14` / `15`。
`verify_writes.py` 的 `BENIGN` 已把这几段加进白名单。

实机验证：用 48000 帧从冷启动把游戏推到存档界面，显示
`保存 / 读取 / 删除` 与 `□ / 游戏 0时 40分` ✓。

> **验收提醒**：即时存档里带着**当时的 VRAM**，所以读旧存档看不出改动；
> 要重新进入（或重开）存档界面才会用到 ROM 里的新图块 —— 和第十二节同一个道理。

## 十五、别再对搬迁后的资源块做「自引用指针」批量重写（重要教训）

**症状**：`ss1..ss5` 五个即时存档读进去后，对白台词**字挤在一起 / 缺笔画 / 出现方块乱字符**，
存档界面的笔记本背景也花。

**排查**：`.ssN` 是 PNG 容器，自定义块 `gbAs` 是 zlib 压缩的 `GBASerializedState`
（0x61000 字节：`0x400` I/O、`0x800` 调色板、`0xC00` OAM、`0x1000` VRAM、`0x19000` IWRAM、
`0x21000` WRAM）。把它解出来就能直接看当时的 VRAM：
`tools/render_state.py <ssN> out.png`（我这次新加的取证工具，可逐层渲染、也可渲染精灵层）。

每个存档头 `0x08` 处存着**创建它的 ROM 的 CRC32**，一比就发现存档来自两个版本：

| 存档 | `romCrc32` | 对应的构建 |
|---|---|---|
| `ss4` `ss5` | `0853175B` | 提交 `c893115` / `be82599` |
| `ss1` `ss2` `ss3` | `6F7FD312` | 当前 `out.gba`（是「读了旧存档后再存」的，所以继承了坏快照）|

**根因**：提交 `8957a59` 为了修花屏，在搬迁 `e852..e1006` 整块时加了一段启发式：
「块内任何落在旧地址区间的 u32 都当成自引用指针，+delta」。这个判据是**假阳性陷阱** ——
这个块主要是 4bpp 美术数据，字节组合本来就会频繁形成 `0x00800000..0x0092A6C0` 这样的值。
它误改了 **876 处**，每一处的特征都是**最高字节 0x08→0x00 / 0x09→0x0A**（就是"值 + delta"），
把笔记本背景和剧本流都改坏了。

**铁证**：上一次正常工作的构建 `c893115` 里，搬迁后的块与**日文原版对应块逐字节相同** ——
也就是说块内根本没有自引用需要改，只有 FAT 项搬家，游戏是通过 FAT 定位这个块的。

**修法**：删掉那段重写（`build_rom.py` 里有注释说明）。重建后：

| 兼容面 | 结果 |
|---|---|
| FAT（1200 项） | 与 `c893115` **完全一致** |
| 字库表（FAT 850，`0x800000`） | **逐字节一致** |
| 步进表（FAT 851，`0x6A4840`） | **逐字节一致** |
| 搬迁块（`0x864080`） | **逐字节一致**（= 日文原版块） |
| 追加剧本区（`0x8B14C0` 起） | **逐字节一致** |
| 与 `c893115` 的全部剩余差异 | 仅 186 字节，都在 `0x44F5CA..0x44FB68`（存档/指令菜单牌子的抗锯齿，`d4bed42` 的有意改进）|

因此**旧存档（`ss4`/`ss5`）在新 ROM 上可用**：字形索引、步进表、剧本偏移全部没变。

> 原则：想改"搬迁后块里的绝对指针"，必须先证明那些字**真的是指针**（例如它是某个指针表的一部分、
> 改写后落在新块区间内）。只凭"值落在旧地址区间"就批量 +delta，必然误伤美术/剧本数据。

## 十一、控制码串与「无假名」串的大漏译（已修复）

两个**提取器的过滤器**把整类可显示文本挡在了主表之外。它们都是为了防止位图数据
被当成文本而设的，代价是漏掉真文本：

| 漏译类别 | 被谁挡掉 | 规模 | 处理 |
|---|---|---|---|
| 含控制码的串（`0xFFC2/0xFFC0` 高亮、`0xFFA2+0xFE03` 场景卡、`0xFE02/0xFE04` 定位码、`0xFFF2/0xFFF3` 人名高亮） | `export_script.read_string` 里 `code > GLYPH_MAX(0x6A8)` 直接 `return None` | **274 条** | `tools/add_ctrl_rows.py` + `data/ctrl_translations.tsv` |
| 串池里**没有假名**的串（片假名地名表、人物档案数字、staff 名单、`」フン“““` 这类短句） | `extract_pool.scan_pools` 要求串里必须有平假名；且只扫偶数字节偏移 | **474 条** | `tools/add_pool_rows.py` + `data/pool_extra.tsv` |

修完主表 **101,754 行**，`verify_rom.py` **101754/101754 完全一致**。

### 11.1 控制码串

- 密码串（`<FFC2>KOHU<FFC0>` 这类 4 字母码）**原样保留**，它们是墙上的密码，不能翻。
- 人物档案的标签（`氏名/職業/年齢/誕生日/血液型`）译成 2 字标签，并把分隔符统一成
  `、、`：原版「标签+分隔」固定占 4 格宽（`氏名、、`=2+2、`誕生日、`=3+1），
  换成 `生日、、` 才能让数值列对齐。
- 场景卡 `[FFA2][FFC2]、、、[FE03]地名[FFC0]` 只翻地名，`、` 的个数一个不动
  （它是排版留白）。
- 译文里控制码写成 `\xXXXX` 转义；`verify_rom.norm_tr()` 会把它归一成 `[XXXX]`
  再和 ROM 解码结果比对。

### 11.2 无假名串（e417 场景名表等）

e417 是**场景名表**（存档界面第二行、状态栏都读它），44 个串里 6 个是片假名/纯汉字，
被 `scan_pools` 的假名过滤全丢了：`西新宿9丁目 / コマ劇場前 / アルタ前 /
コ～ポ中野ハイツ / メゾン西新宿 / アジト`。同类的还有人物档案的年龄档
（`37才`、`41代後半`）、staff 名单（`アソシエイトプロデュ～サ～`、`デ～タ作成`）、
以及 `ダミ～`、`アプロ～チコマンド2`（各场景指令表里的占位项）。

`add_pool_rows.py` 会：

1. 对**每个有串池的条目**、**两种字节奇偶**都做 NUL 分隔扫描；
2. 只保留纯片假名/汉字/数字/标点的串（噪声靠"没写译文"自然排除）；
3. 排除落在偏移表槽位里的串（那是表内串的后缀，写它会覆盖正文——
   本次就抓到并删掉了 2 条这种历史脏行：`e198@28562`、`e311@3000`）；
4. 排除与主表已有文本互为子串的串；
5. 双奇偶可能对同一段字节各报一次，按偏移去重，保证写入区间不重叠。

### 11.3 顺带修掉的管线问题

| 问题 | 症状 | 修法 |

| `verify_rom.GLYPH_MAX` 只有 `0x2000` | 含 `0xFFC2`/`0xFE03` 的串被 `read_string` 拒收，校验时一律 `got None`，新加的 274 行**永远校验不过** | 提到 `0x10000`，并把控制码（`>=0xFE00`）排除出「缺字形」判定 |

## 十二、花屏根因：追加条目没有做 4 字节对齐（已修复）

**症状**：标题 →「继续游戏」→ 读取界面，FILE 01 第二行（地名）显示彩色"花形"乱码块；
游戏内状态栏的地名也残留日文。

**定位过程（全部可复现）**

1. 把存档 PNG 内嵌的那一帧当真值，对每个 8x8 屏幕块用 OBJ/BG 各 bank 反推颜色索引，
   再在整块 VRAM 里搜同内容的 tile → 乱码块 = **OBJ VRAM 最后 4 个 tile（1020–1023）**，
   且这 4 个 tile **每个字节都非 0**，即从未被写过、保留着上一屏位图的残留。
   （过程中修掉 `render_state.py` 的两处 OAM 解码错误：tile 号在 attr2 的 0–9 位，
   调色板 bank 在 attr2 的 12–15 位。）
2. 用 `tools/check_state.py` 判定：`ss2` 9 个文字精灵里 **5 个指向"从未写过"的 tile**；
   `ss4`/`ss5`、日文原版 `ss1`、以及当前构建跑到存档界面的存档都是 0 个。
3. 换用 `.sav` 直接测（关键是 harness 要调 `mCoreAutoloadSave`，
   否则游戏跑在空白卡带上、存档界面永远没有文件——之前就是这么被误导的）：
   标题 →「继续游戏」→ 读取界面，FILE 01 的地名行 **只画了 2 个精灵**，
   而日文原版是 **9 个**（y=25，x=80..184）。
4. 同一帧对比 EWRAM：日文原版在 `0x2030D79` 有解压好的**场景名表**，
   中文版**整张表都不在** → 地名行是从一块没被填充过的缓冲里画出来的。
5. 把 `e417`（场景名表）的 FAT 指回**未被改动的日文原数据** → 地名行立刻正常显示
   （日文）。说明"表没被解压"与内容无关，只与**存放位置**有关。
6. 把**同一份中文压缩数据**搬到 ROM 里一个 **4 字节对齐**的位置、只改 FAT →
   地名行正常显示中文 `大河原家告别式会场`。

**根因**：`import_script.py` 把放不下的条目直接追加到 ROM 末尾，
**没有做 4 字节对齐**。游戏用 GBA BIOS 的 LZ77 SWI 解压，**源地址必须字对齐**；
`e417` 原本在 4 对齐处，追加后落到 `0xBEC5D6`（mod 4 == 2），游戏解压失败，
场景名表没进 EWRAM，界面只好画未初始化显存 → 花屏。

**影响面**：本次构建 **592 个条目被重定位**，其中近一半落在非 4 对齐地址上，
它们**全部**可能在游戏里解压失败（表现是"某些界面数据没加载"，不一定是花屏）。

**修法**：`import_script.py` 追加前把 ROM 长度补到 4 的倍数。

**验证**：修复后 592 个重定位条目**全部 4 对齐**（与日文原版一致：941/231/184/39），
`verify_rom` 101754/101754、`verify_writes`、`verify_glyphs` 全绿；
用 `.sav` 走「继续游戏 → 读取」地名行显示正确的中文。

**给测试的教训**：harness 必须调 `mCoreAutoloadSave()`（前端都会调），
否则 `.sav` 根本没被加载，会得出"存档界面本来就是空的"这种错误结论。

### 12.2 指令牌子有**两套**（都已在 `patch_save_plates.py` 里处理）

同一批 11 个指令项在 ROM 里存在**两份**，`0x66C400 + n*0x200` 和 `0x66DC40 + n*0x200`：

| 套 | 基址 | 配色索引 | 出现场合（实测） |
|---|---|---|---|
| A（深） | `0x66C400` | 字身 `1`，填充 `4–7` | 指令菜单列表（ss2 左侧） |
| B（浅） | `0x66DC40` | 字身 `9`，填充 `10–15` | 左上角动作提示（`タバコを吸う`）等高亮态 |

之前只改了 A 套，所以 ss1 左上角仍是 `タバコを吸う`。B 套的调色板与标题菜单牌子相同
（`patch_menu_plates.py` 里 `CORE=9/AA=12/FILL=15`），必须单独指定 ink/fill，
否则 `auto_box` 找不到字身会整块跳过。

> 顶部状态栏（`大河原家 応接室 | パートナー | 3/11昼`）**不是字库文本、也不是这两套牌子**：
> - `パートナー` 是 ROM `0x472530..0x4725F0` 的现成 8×8 图块，**已重画为「助手」**（见 13.3）；
> - `3/11昼` 是 `0x460E30..0x460F50` 的现成图块；
> - 房间名（`応接室`/`廊下`）的图块在 ROM 里**原始和逐条目解压都搜不到**，
>   是游戏运行时自己渲染进 BG 图块的，来源是场景名表 `e417`。

### 12.3 放得下的条目改为**原地回写**（防止硬编码读取）

`import_script.py` 原来只在「新数据 ≤ 原 FAT 尺寸」时原地回写，否则一律追加到 ROM 尾部。
但游戏里**有些代码路径不是通过 FAT、而是按硬编码地址**读条目的（顶部状态栏的场景名疑似如此）。
追加会把条目搬走，硬编码读取者仍然看到旧（日文）字节。

现在多一个判据：**只要新数据放得进「本条目起始 → 下一条目起始」之间的空隙，就原地回写**
（并更新 FAT 尺寸）。本次构建因此多了 3 个条目留在原址，其中包括场景名表 `e417`
（`0x39EE50`，原 1204 → 新 1210，空隙 1216 字节，刚好放得下）。

> 对 `e417` 的验证仍是"未定"：用它做了 in-place 之后，从旧即时存档里看到的状态栏地名没变，
> 但**状态栏在存档快照里不会重画**，所以这个观察不能作为判据。需要一次真正的换场景才能确认。

## 十三、预渲染「页面」：开场声明页与标题封面

有一类画面**不是字库文本**，而是一整张预渲染「页面」：开场声明页（
`この物語はフィクションです…`）和标题封面（`探偵 神宫寺三郎 / 白い影の少女`）都是。
`translation.tsv` 里搜不到它们，`docs` 旧文里的「尚未覆盖」指的就是这些。

### 13.1 页面结构（两页完全一致）

页面是 e840 档案里的一个 **LZ77 blob**（BIOS 0x10 头，游戏用 SWI 解压），
解压后 **20848 字节 = 0x5170**，布局固定：

| 偏移 | 内容 |
|---|---|
| `0x0000` | 32 字节头部（`0x5170`、30、20、`0x04B0`… 等尺寸/计数） |
| `0x0020` | **600 个 4bpp 图块**（`0x4B00`），图块号 T 的字节在 `T*32` |
| `0x4B20` | **13 组 16 色 BGR555 调色板**（`0x01A0`） |
| `0x4CC0` | **600 条 u16 图块表项**（`0x04B0`），低 10 位 = 图块号-1，高 4 位 = 调色板 bank |

表项 i 对应屏幕第 `i/30` 行、第 `i%30` 列（30×20 格铺满 240×160）。
游戏的加载代码把尺寸写死，解压到 EWRAM `0x02027800`，再从 `+0x20` 起 DMA 到
BG 图块区（所以头 32 字节不会被当成图块，**不能被覆盖**）。

定位方式（两页通用）：e840 的偏移表在文件 `0x472850`，表项是相对 e840 起点的
u32；代码里的 base 常量是 `0x08472850`。

| 页面 | 表项位置 | 表项值 | blob 文件偏移 | 工具 |
|---|---|---|---|---|
| 标题封面 | `0x472B88`（第 206 项） | `0x107CD0` | `0x57A520` | `patch_title_page.py` |
| 开场声明页 | `0x472BE0`（第 228 项） | `0x112E00` | `0x585650` | `patch_disclaimer_page.py` |

### 13.2 标题封面：以手修图为准

标题画面 = BG3 上的这张页面（另加 OBJ 层的 `PRESS START BUTTON` 文字 13 个 8×8 精灵）。
`tools/patch_title_page.py` 把 **`docs/title/标题画面_BG3原画.png`（240×160）当母本**导入：

* 只重写「与页面当前渲染不同」的格子，其余图块逐字节不动；
* 每个要改的格子从 13 组调色板里**挑误差最小的那组**，并同步改该格表项的 bank 位；
* 调色板本身不改（每组的 15 个色号在原画里全都用满了，没有可挪用的空位）；
* 新流压完 **13883 ≤ 13962 字节 → 原地回写**；万一某次改大了放不下，就追加到 ROM 尾部
  并把表项指过去（blob 必须 4 字节对齐）。

**一个格式限制**：一个图块只能用一组调色板。若手修时把两组调色板的颜色画进了同一格，
导入后这些像素只能就近取色 —— 当前实测 38400 像素里 1004 个有偏差（其中 795 个 RGB
距离 <10，1 个 57），肉眼基本看不出，`--check` 会把分布打出来。

导出/验收素材在 `docs/title/`：`标题画面_240x160.png`（完整画面，取自真机启动截图）、
`标题画面_4x.png`、`标题画面_BG3原画.png`（**手修母本**）、`标题画面_OBJ文字.png`
（按钮文字层 = 完整画面减 BG3）。

### 13.3 顶部状态栏的 `パートナー` → `助手`

状态栏标签是 e833（**未压缩**条目，文件 `0x472390..0x472610`）尾部的 8×8 图块：
上半 `0x472530/550/570/590`、下半 `0x4725B0/5D0/5F0`。牌子第 8 格（下半 x24..31）
不属于 e833 —— 游戏在那儿画状态栏边框图块，所以新标签下半必须留在 x0..23 内。

图块是 4bpp，用状态栏自己的调色板（bank 13）：字身 `6`、1px 抗锯齿 `9`，
底色 `12/13` 逐行交替（每 8 行里第 2、5 行是 12，其余 13）。
`tools/patch_status_bar.py` 把旧假名擦回**该行底色**，再用 STHeiti 9px（墨迹 8px 高，
与原假名同一条文字带）画「助手」+ 右侧/下方 1px 抗锯齿。
zpix 是 11×11，压到 8~9px 时「助」的笔画会糊在一起，所以这里用与其它牌子相同的字体。

`verify_writes` 的白名单加了 `(0x472530, 0x472610)`。

### 13.4 验收方式（重要）

**不要用即时存档验收这两页**：存档里 VRAM/图块表是快照，而且游戏的图块表在 RAM 里
还有一份，存档注入的 bank 位会被它覆盖，看到的是旧配色。

正确做法是从冷启动走一遍：
`work/bin/autoplay <rom> <script> <outdir>`，脚本 `wait 480 → mash A 6 → wait 120 →
mash START 4 → wait 260 → shot title`（480 帧是声明页，按掉之后是标题画面）。
实测：真机截图的 BG3 与 ROM 里 blob 的渲染 **逐像素 0 差异**，说明导入的图块表 bank 位
在真实流程里生效。

## 十四、文案精修（AI 逐行翻译留下的痕迹）

初版译文是**逐行独立翻译**的，而游戏把一句话拆成一行一个「显示行」，
于是日文的语序（谓语在句末）被照搬进中文，读起来大量倒装；再加上若干直译，
就成了"能玩但一言难尽"的观感。典型例子（序幕）：

    俺はふてくされた顔で       → 我带着不满的表情      ✗
    この会場から出て行く女性に   → 向正走出会场的女性     ✗
    目がとまった，            → 目光停住了，          ✗
    （三行连读：我带着不满的表情向正走出会场的女性目光停住了）

正确做法是**把动词提前、让宾语跨行**，行数/标点/行长都不动：

    我板着脸 / 目光停在了正走出会场的 / 女性身上，

### 14.1 硬约束：每行字数不能超过该行日文的字数

池里的每个串占固定槽位，`translation.tsv` 第 4 列 `n_codes` 就是该行允许的字数。
超了 `import_script` 会**保留日文**（构建仍会成功，只是那行没换成中文），
所以精修只能靠调语序，不能靠加字。标点也必须与日文一一对应：
行首的 `、」『“`、行尾的 `，。！？『` 一个都不能多、不能少、不能换位置；
`“““`（游戏的省略/结巴码）原样保留。

### 14.2 工具链

| 工具 | 作用 |
|---|---|
| `qa_translation.py` | 按机械特征给译文打分：`neg`（日文否定被丢）、`neg+`（中文凭空加否定）、`calque`（直译腔）、`number`（数字不一致）、`punct`（标点错位）、`stray`（残留 `～＋－`/ASCII）、`short`（内容被砍）、`over`（超槽位）、`kana`（残留假名） |
| `export_qa_context.py` | 把 worklist 切成带上下文的复核块（每条 flagged 行前后各 2 行），合并连续行 |
| `apply_cn_patch.py` | 把 `entry<TAB>idx<TAB>新译文` 打回 `translation.tsv`（留 `.bak`），超预算会报 `OVER BUDGET` 并非 0 退出 |
| `validate_cn_patch.py` | 提交前的机械校验：槽位、标点首尾、`“` 个数、数字、控制码转义 |

用法：


### 14.4 按源文广播的例外

同一句日文在**不同场景**可能意思不同。实测 `、なかったようですね『`：

* e1:53（葬礼上，助手刚说"应该是母亲"）＝「不用我多嘴提醒」；
* e23:301（另一处，前一行是"看来并不是"）＝「并不是邪恶组织」。

所以 `apply_cn_by_jp.py` 的广播不是万能的：这类句子要用
`apply_cn_patch.py` 做**单行**修正，而且**必须在广播之后**执行，否则会被覆盖。
复核者遇到这种情况应当在补丁里单独标注（同一个 (日文, 旧译文) 键不能有两种新译文）。

### 14.5 场景推进分类：先拿到"同一段对话"，再改语序（2025 收尾）

逐行精修解决不了语序：要修 `俺はふてくされた顔で / この会場から出て行く女性に /
目がとまった，` 这一句，必须同时看到三行。所以先把全表按**剧情推进**分类成场景。

**存储顺序 ≠ 剧情顺序**，三处证据：

1. `data/translation.tsv` 的**行序是 `(entry, idx)`**（全表 101,795 行里只有 e1 的 4 个
   池串例外）。`entry` 是 FAT 条目，`idx` 由两个抽取器建立：偏移表槽位升序，
   无偏移表的「池串」由 `extract_pool` **追加在表行之后**（132 个混合条目里，
   没有任何池串落在表行 idx 区间内，所以两套确实是拼接而非交错）。
   校验：表行的绝对偏移 `base + offset` 在 ROM 里 99.2% 能解回记录原文
   （358 行不符的是密码/ASCII 行，属正常）。
2. 同一个条目里**物理上分成若干串段**：一段是剧情正文，一段是存档/菜单系统串，
   一段是地点与道具串。段与段之间偏移会**回跳**——这就是场景切分点。
   例：e1 = 序幕正文 `0..161` / 洋子问候与主人公独白 `162..202` / 地点与道具 `203..226`
   （旧文档里"e1 顺序混乱"的印象，来源就是这三段在探测顺序里交错）。
3. 同一段文本会在**多个条目**里重复：e80 / e126 / e173 / e215 是同一份 990 行文本，
   e1 的独白段在 e2 里再次出现。所以"改一条台词"能同时修好别处的实例
   （见 14.4 的反例：不同场景同句异义要用单行补丁）。

**产物**（`tools/scene_index.py`）：

| 文件 / 命令 | 内容 |
|---|---|
| `data/scenes.tsv` | 场景目录：`scene / kind / entry / idx 范围 / rows / codes / 地点 / 在场 / note` |
| `data/scene_lines.tsv` | 每行 → `scene / pos / join`（`>` 接下行、`<` 承上行、`<>` 中间行、`-` 收尾） |
| `scene_index.py build --report` | 重建上面两个文件（795 个场景；`kind` = scene / system / quiz / chara / credits / trivia） |
| `scene_index.py list --kind scene` | 场景清单 |
| `scene_index.py show 3.0` | 按剧情顺序逐行读出（日文 ｜ 现译） |
| `scene_index.py check` | 校验 101,795 行全部有场景归属、场景内 `pos` 连续 |
| `tools/export_scene_context.py` | 导出成批复核文件（整场景、含跨行标记与字数预算） |

```bash

python3 tools/scene_index.py list --kind scene | head
python3 tools/scene_index.py show 1.0
python3 tools/export_scene_context.py --entries 1-20 --out work/scenes/e1_20.tsv
```

规模（`scene_index.py build --report`）：455 个条目 → **795 个场景**，
其中剧情场景 625、问答/审讯分支 136、人物资料 14、STAFF 18、彩蛋 2；
剧情场景 625 个，中位 25 行，最大 1028（e42 酒吧）。
**41% 的行（42,067 / 101,795）是跨行句的中间行** —— 也就是说近一半的行单独看
都不成句，这正是必须按场景成批复核的量化理由。

### 14.6 风格规则（减少倒装 + 冷峻笔法）

`data/translation_rules.md` 新增：

* 一.13 **禁止倒装**：不得照抄日语语序（动词提前、修饰语跨行跟随，行数/标点/槽位不动）；
* 一.14 **行尾不落光杆动词**：`…浮现出来，`、`…退去，`、`…被拍了下来，` 要换成
  名词性落点或补小宾语；`被 + 动词 + 了` 改主动；
* 二 **冷峻笔法**：能短则短、少用虚词连词、不堆语气词（`呢/吧/啊/呀/哦` 只给性格轻佻的
  角色）、不加戏（不靠感叹号与煽情形容词）。

量出来的语料特征（全表）：`被` 889、`因为` 512、`感到/觉得` 1078、`非常/十分/相当` 517、
`的样子/的存在/有着` 508、语气词 20,697（20.3%）、`是…的` 731、中文句尾落在光杆动词的
句单位 2,026（3.4%）。这些都是复核时的搜索词。

### 14.7 标点规则的已知例外（现今 7 行）

一.1 要求"标点种类、数量、顺序完全一致"，但中文句读与日文并不一一对应：
`色々考えたが` 这类行日文无标点，中文写成 `想了很多，` 更自然。全表有 **231 行**
属于这一类**只增句读**的差异（`tm.py check` 报 `punctuation`，全部是"日文无、中文有"）。
判定标准：**只允许加句读（`，。`），不允许删、换位置、改种类**；`“““`、`々→…`、
括号与控制码一律照旧。补丁里遇到这类行要在补丁文件头注明。

**2025 收尾的批量同文对齐把例外从 180 行压到 7 行**：全表同文对齐
（`work/scenes/patch_global_mirror.tsv`，8,246 行）把已定稿条目的译法铺到其余条目的
同文行后，原先"只加了一个句读"的行都被规范成了定稿译法，`tm.py check` 因此只剩
7 行真例外：`3:48`（`』さん＋` 记账）、`3:52`、`3:146`、`3:227`、`5:21`、`1:3`、`2:140`。

**数字区间里的 `。`**：剧本把「六、七年前」写作 `6。7年前`（24 行，e168/e170/e314/
e315/e503/e505 等）。中文写成汉字数字 + `、`（`六、七年前`），`tm.py` 的
`RANGE_DOT` 会把 `数字。数字` 里的 `。` 视作 `、` 再比标点，否则每一条区间都像违规。

**控制码不再计入标点**（2025 修正）：JP 源用 `[FFC2]`、译文用 `\xFFC2` 表示同一段
颜色/人名码，原来的 `punct_skeleton` 不认这两种写法，于是 `＜＞` 被当标点，
45 行人物资料被误判。现在 `tm.py` 的 `punct_skeleton`/`slots_used` 先剥掉
`[XXXX] <XXXX> \xXXXX`，同时**长度预算也按剥离后计算**——否则
`\xFFC2姓名\xFFC0、神宮寺、三郎` 会被当成 13 字而拒收（实际 7 码）。

**人物资料行的顿号重复（45 行，有意保留）**：`[FFC2]誕生日[FFC0]、3月7日` 这类行，
上一行已经以 `[FFC0]、` 收尾，中文按分字段写成 `\xFFC2生日\xFFC0、、3月7日`
（两个顿号）。若只写一个，游戏里两行连读就只剩一个顿号，字段划分消失。
所以这 45 行保留重复顿号，属**已知例外**，不是漏改。
（e3[48] `、』さん＋付けで` → `、在名字后加了『小姐』` 是另一种例外：
`』…＋` 是游戏表示"名字后加称谓语"的记号，中文写成 `『小姐』`，括号种类因此变化。）
