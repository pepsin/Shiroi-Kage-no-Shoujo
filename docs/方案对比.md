# 汉化技术方案对比（调研）

> 目标：把日文原版《侦探神宫寺三郎 — 白影的少女》变成可玩的中文 ROM。
> 全部数据为**本项目实测**，不是估算。

## 〇、硬约束（实测）

| 项 | 数值 |
|---|---|
| 剧本 | 45488 行 / 190 条目 / 约 47 万字符 |
| 译文用字 | **2102 个不同汉字**（已尽量用常用字） |
| 日文字库 | 1704 槽；其中 **931 个**译文可以直接复用，**1171 个要新做** |
| 空槽 | 771 个（脚本不引用；但**不能断定**其它资源也不用） |
| 字形格式 | 16×16、4bpp、0x80 字节/字（不可压缩到更小） |
| 编码 | `表下标 = 码位 − 1`（码位 ≥ 0x20）→ 要放 2102 字，码位必然到 **0xB3A** > 原上限 0x6A8 |
| 尾部连续空区 | **203 KB**（`0x7CE6C0..0x800000`） |
| ROM 实际数据量 | 中文版 7.87 MB（8 MB ROM **装得下**，只要重新紧凑排布） |

**两个绕不开的点**

1. 2102 > 1704 → 字形表**必须扩容**，`码位 > 0x6A8` 无法回避（除非改代码，或改译文用字）。
2. 扩容后的表 285–384 KB，比尾部 203 KB 空区大 → 要么 ROM 扩一点，要么全量重打包腾地方。

## 一、字形方案

### A. 只追加 + 整表搬到 0x800000（**当前已实施**）

新字全部追加在表尾，原 1704 槽一个不动，表 3003 槽放 `0x800000`，FAT e850 改指。

* ✅ 零风险：标题/菜单/图形界面仍然拿得到原字形
* ✅ 不需要改代码；已验证：标题、职员表、声明画面与日文版**逐像素一致**
* ✅ ROM 内文本往返 **45484/45484 完全一致**
* ⚠️ 码位到 0xB3A（引擎是否接受未实测；静态搜索**未见** 0x6A8 字面量，风险低）
* ⚠️ ROM 9.42 MB（非 2 的幂；模拟器无影响，个别烧录卡要求 2 的幂）

### B. 回收空槽（缩到 2232 槽）

把 771 个脚本不引用的槽（**全部假名 + 612 个汉字**）改写成新字，只追加 400 个。

* ✅ 表小 98 KB；仍要追加 400 槽 → **码位照样超过 0x6A8**，风险只减少不消除
* ❌ 会毁掉 `×`、`■`、全部假名、612 个汉字字形
* 实测：标题（其中「偵」正好被回收）、职员表、声明三处画面**都没被打坏**
  → 说明这些画面是**预渲染图形**，不走字库；但菜单/对白处**无法证实安全**
* 结论：省不了多少空间，却引入不可验证的破坏风险，**不建议**

### C. 改代码：第二字库页（code ≥ 0x8000 走新表）

把 400+ 个新字放第二张表（尾部/扩展区），打补丁让文本引擎按码位选表。

* ✅ 主表不动、码位不必超 0x6A8、ROM 可保持 8 MB
* ❌ 需要 ARM 反汇编 + 代码注入，工作量和风险都最高（GBA 8 MB 已满，还要腾注入空间）
* 适合：A 方案实测被引擎拒绝时的兜底

### D. 约束译文用字（不扩容）

改写译文，只用日文字库已有的 931 字 + 假名外可用字，把不同汉字数压到 ≤1704。

* ✅ ROM 不变、码位不越界、零风险
* ❌ 要砍掉 1171 个简体字 → 只能用日文/繁体形（`記録` 而非 `记录`），**与「简体中文」目标冲突**，可读性明显下降
* 仅作为「引擎拒绝高码位」时的最后手段

## 二、版面 / 体积方案

### E. 当前版：表放 0x800000 + 追加条目 → **9.42 MB**

简单、已验证，代价是文件大 1.4 MB（字体表 0.37 + 重压后放不下的条目 1.06）。

### F. 全量重打包（紧凑排布）→ **≈ 8.0 MB**

实测：中文版**实际数据量只有 7.87 MB**，8 MB 装得下。
现在之所以 9.42 MB，是因为 150 个条目重压后比原槽大、被追加到末尾，
而它们原来的空间（**1.23 MB**）变成了死区。

* 做法：按 FAT 把所有活条目紧凑重排 + 新字库表放进 8 MB 内，重写全部 FAT
* ✅ 文件保持 **8 MB（2 的幂）**，烧录卡/模拟器都最省心
* ⚠️ 需要先做一次「全 ROM 搜索硬编码地址」审计（确认没有代码直接引用被搬走的偏移）
* 工作量：中等（写一个重排器 + 审计），风险可控

### G. 只回收死区 + 表放旧字库位 → ≈ 8.2–8.4 MB

不整体重排，只把追加条目塞进「老字库表原址 218 KB + 尾部 203 KB + 搬迁死区」。
比 E 省 1 MB 左右，比 F 保守。

### H. 字库表压缩后塞进 203 KB 尾部 → 保持 8 MB

字库表 LZ77 压到 ~57 KB（实测压缩率 21%），尾部完全放得下。

* ❌ 字形是被**随机下标直接索引**的（日文原版 218 KB 裸表），不经过解压；
  且解压后 384 KB > GBA 的 256 KB WRAM，**基本不可行**
* 仅当确认引擎对字库资源走的是通用解压加载时才成立（未证实，不推荐）

## 三、未汉化资源（图形文字）

实测确认：**标题「探偵 神宮寺三郎」、开场职员表、虚构声明全是预渲染图形**（不是字库文字），
所以它们不会随译文变化。可选：

* **不管**（英文职员表 + 一句日文声明，不影响游玩）
* **改图**：定位这些 BG 图块，把文字重绘成中文再写回（纯美术工作，与字库方案无关）
* 顺带发现：这些图形画面**不受字形扩容影响**，是 A 方案安全性的又一佐证

## 四、字形的观感（可选优化）

新字形目前用 macOS 系统字体渲染成 16×16。实测三方对比（游戏原字形 / 系统字体 / GNU Unifont）：

* **游戏原字形**：笔画 2px，粗壮的点阵黑体
* **当前系统字体**：粗细、重心都接近原版 → **观感最搭（保持现状即可）**
* **GNU Unifont**（[16×16 点阵](https://unifoundry.com/pub/unifont/)）：1px 细线，**明显偏细**，
  和原字形并排会「一半粗一半细」→ 不推荐
* 想再优化可试 [Zpix / 最像素](https://github.com/SolidZORO/zpix-pixel-font) 这类**粗体点阵中文**，
  或借用参考中文版 `[CGP](简)` 的手调字形（需重建其 码位↔字 映射）

## 五、推荐

| 目标 | 方案 |
|---|---|
| **现在就能玩** | **A + E**（已完成、已三重验证） |
| 想让 ROM 回到 8 MB / 烧录卡友好 | **A + F**（全量重打包，需地址审计） |
| 若实机发现高码位显示异常 | **C**（第二字库页）兜底，或 **D**（约束用字） |
| 想更接近原生观感 | 换点阵字体渲染字形（第四节） |
| 想让开场声明/职员表也中文 | 改图（第三节） |

**当前唯一未闭环的验证**：对白框内的高码位字形是否正常显示。
无头模拟器跳不过本作很长的开场演出（游戏在演出期间不接受按键，已确认模拟器 KEYINPUT 正常），
需要一次人工试玩确认。
